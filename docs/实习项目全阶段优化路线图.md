# shopkeeper-agent 实习项目全阶段优化路线图

## 目标

把项目从“能把自然语言转 SQL 的学习项目”做成一件面试时能完整讲清的工程作品：有真实业务问题、有可靠结果链路、有权限和恢复边界、有质量评测，也能在几分钟内稳定演示。

简历项目最重要的不是功能数量，而是每一层都能说清楚“解决什么问题、怎么实现、如何验证”。因此后续优先做可见、可测、可讲的能力，不把时间耗在暂时无法证明价值的重基础设施上。

## 当前基础

第一阶段已覆盖以下核心能力：

- FastAPI + LangGraph 的自然语言问数工作流，包含召回、改写、SQL 生成、校验、执行、图表和解释。
- JWT 身份、RLS、列脱敏、SQL 安全防线。
- MySQL 持久化会话、查询快照、短上下文、幂等请求键与 SSE 终态。
- 历史会话、刷新恢复、CSV 导出、表格分页和精确金额排序。
- 真实 MySQL 并发幂等冒烟，以及后端单测、Ruff、前端生产构建。

这些足以支撑“可靠的多轮问数”主线。接下来不应重复做会话或聊天 UI，而应补齐语义治理、质量证明、工程交付与面试材料。

## 总体优先级

| 优先级 | 阶段 | 招聘价值 | 推荐投入 |
| --- | --- | --- | --- |
| P0 | 整理第一阶段并做稳定演示 | 没有它，已有功能无法可信展示 | 1–2 天 |
| P1 | 业务字典、收藏、纠错反馈 | 把 Demo 变成“可迭代的数据产品” | 4–6 天 |
| P1 | 评测集与质量报告 | 能回答“准确率怎么证明” | 3–5 天 |
| P1 | CI、部署、演示材料 | 让项目可交付、可复现 | 2–3 天 |
| P2 | 观测与性能治理 | 展示工程意识与定位能力 | 3–5 天 |
| P3 | 后台任务、多 worker、复杂报表 | 有真实需求或充足时间再做 | 后置 |

如果只剩两周，完成 P0 + P1 即可；它们比新增十个聊天按钮更能提升简历质量。

## 阶段 0：把第一阶段收口为可展示版本

### 要做什么

1. 提交并整理当前第一阶段改动，避免面试时运行的代码与 GitHub 不一致。
2. 在 README 写出一键启动、数据库迁移、演示账号、测试命令和能力边界。
3. 录制或准备 3–5 分钟演示：登录 → 问数 → 追问 → 刷新恢复 → 排序/导出 → 切换账号隔离。
4. 在项目根目录加入架构图和数据流图，说明 React、FastAPI、LangGraph、MySQL、Qdrant、ES、数仓之间的关系。

### 面试可讲

“我没有只依赖 HTTP 200 判断查询成功。查询先在 MySQL 预登记，SSE 只在终态成功持久化后才向页面确认；断流时用 `client_request_id` 恢复同一轮执行，避免重复跑 SQL。”

### 完成标准

- 新机器按 README 可启动。
- `uv run pytest`、`uv run ruff check app tests`、`pnpm lint`、`pnpm build` 全部通过。
- 每个演示账号看到的会话和导出数据符合权限范围。

## 阶段 1：业务字典与语义治理

### 为什么优先做

Text-to-SQL 最大的问题不是“能否调用模型”，而是“GMV、销售额、活跃用户”等业务词到底代表什么”。业务字典能直接回答这个问题，也是数据平台和智能分析岗位最容易认可的设计。

### 功能

- 管理员维护术语、定义、别名、标准口径提示和启停状态。
- 示例：`GMV`、`成交总额`、`交易额` 指向同一术语，并明确标准口径。
- 查询前只注入已启用的字典文本；字典不能覆盖指标口径、RLS、脱敏、时间解析和 SQL Guard。
- 普通用户只读，管理员可以维护；术语修改留更新时间和操作者。

### 技术落点

- Meta MySQL 新增 `business_glossary`。
- FastAPI 增加管理员 CRUD、普通用户只读 API。
- `QueryService` 在构造 Agent state 时读取受限字典文本；`generate_sql.prompt` 明确字典优先级。
- React 做轻量管理面板，不引入后台系统或组件库。

### 验收

- 管理员新增术语后，下一次查询的 Agent 上下文包含该术语。
- 停用术语后立即不再注入。
- 非管理员写入得到 403；同名术语得到 409。

## 阶段 2：收藏问题与人工反馈闭环

### 为什么优先做

这让项目从“一次性问答”变成“可复用、可纠错的分析工具”，并给后续评测留下真实输入来源。

### 功能

- 用户把已完成查询收藏为常用问题，可重命名、删除、一键回填输入框。
- 结果气泡提供“有帮助 / 需纠正”；负反馈可填写一句原因。
- 反馈与收藏必须按 owner 和当前 scope 校验，不能利用 run_id 跨账号读取信息。
- 同一用户同一 run 的反馈采用 upsert，不产生重复记录。

### 面试可讲

“模型输出不是黑盒终点。我把用户反馈关联到脱敏快照、SQL 解释、权限上下文和 trace，后续能按失败原因收集评测样本，而不是只看主观好不好用。”

### 验收

- 刷新后收藏仍存在，点击只回填而不自动执行。
- B 账号不能收藏或评价 A 账号的 run。
- 一条负反馈能在后台列表中定位到对应 run、SQL 和上下文。

## 阶段 3：评测集、质量报告与回归门禁

### 为什么优先做

面试官很容易问：“你如何判断 Agent 真的更准确？”没有评测集，就只能回答“我自己试过”。这是最需要补上的证据。

### 功能

- 建立 30–50 条可复跑问数样例，按简单聚合、多表关联、时间表达、权限过滤、脱敏、澄清、恶意输入分类。
- 每条记录期望指标、维度、时间范围、权限结果和 SQL 关键片段；不强求完全 SQL 字符串相同。
- 脚本输出通过率、失败分类、耗时、token、典型失败样例。
- 每次修改 prompt、字典或安全规则时，执行回归集并比较结果。

### 技术落点

- 扩展已有 `app/scripts/run_cases.py`，结果输出到 `reports/`。
- 把外部模型不稳定性和确定性规则分开统计。
- 先用 Markdown/JSON 报告，不急着做评测平台页面。

### 验收

- 任何人能用一条命令复跑样例。
- 报告包含真实运行日期、模型版本、样例数、成功/失败分类；不编造准确率。
- 改动安全规则后，RLS、脱敏、SQL 拦截用例不能回退。

## 阶段 4：可观测性与性能治理

### 为什么做

项目已有 trace 基础。把它变成可解释的性能数据，会让你从“会调模型 API”提升到“能定位生产链路问题”。

### 功能

- 展示一次查询的节点耗时、模型调用次数、token、SQL 执行耗时、失败归因。
- 为慢查询设置阈值和提示，区分检索慢、LLM 慢、SQL 慢、写历史失败。
- 增加查询限流与每用户并发限制，错误返回可理解的提示。
- 建立最小性能压测：并发用户数、P50/P95、超时率。

### 技术落点

- 复用 `trace` / `trace_span`，在现有 `show_trace.py`、`report_obs.py` 上做报告。
- 限流先用进程内令牌桶；多实例部署时再改 Redis。
- SQL 执行继续保留行数和时间预算，不做盲目缓存。

### 验收

- 任选一次慢查询，能说明慢在哪个节点和下一步优化方向。
- 超过并发限制的请求不会压垮服务，也不暴露内部栈信息。

## 阶段 5：工程交付与部署

### 要做什么

- GitHub Actions：后端 pytest + Ruff、前端 lint + build。
- 完整 Docker Compose：前端、后端、MySQL、Qdrant、ES、Embedding；区分开发和演示环境变量。
- `/health` 升级为依赖健康状态，明确哪些服务未就绪。
- 增加 `.env.example`，绝不提交密钥或真实业务数据。
- GitHub README 放架构图、截图、能力清单、运行命令和已知限制。

### 面试可讲

“我把模型、向量检索、元数据和数仓依赖容器化，并用 CI 阻止后端规则或前端构建回归。Demo 环境与本地开发环境分开，密钥只来自环境变量。”

### 验收

- 新环境复制 `.env.example` 并按 README 启动。
- Pull Request 或 push 自动执行检查。
- 演示环境不使用管理员默认弱口令或真实生产数据。

## 阶段 6：作品呈现与投递材料

### GitHub 首页应有

1. 一张架构图。
2. 一段 30 秒 GIF 或短视频：输入问题到结果、历史恢复、CSV、权限切换。
3. 功能亮点和技术取舍，不要只罗列框架名。
4. 可复现实验命令和评测结果。
5. 明确能力边界：教学数仓、演示鉴权、单 worker 恢复等。

### 简历建议描述

> 基于 FastAPI、LangGraph 和 React 实现电商智能问数系统，构建“检索增强—SQL 生成校验—权限过滤—结果快照”链路；使用 MySQL 持久化会话与查询终态，通过 SSE 幂等恢复避免断流重复执行，并支持 RLS、列脱敏、历史追问、精确金额排序与 CSV 导出。构建业务字典与离线评测集，持续回归问数质量与安全策略。

### 面试准备的四个故事

| 问题 | 你要讲的案例 |
| --- | --- |
| 如何保证安全？ | JWT 身份、RLS、脱敏、SQL Guard 四层防线。 |
| 断网或重复提交怎么办？ | 预登记 run、`client_request_id`、数据库终态优先、SSE 恢复。 |
| LLM 结果不准怎么办？ | 业务字典、冻结指标口径、评测集、负反馈沉淀样本。 |
| 性能慢怎么办？ | trace 定位、召回并发控制、SQL 预算、分层治理。 |

## 暂时不要做

- 自建复杂后台管理系统、工作流编排平台或 BI 报表设计器。
- 一开始就上 Celery、Kafka、Redis 集群、多 worker 分布式恢复。
- 用“准确率 90%”“节省 80% 时间”之类没有真实评测支撑的数字。
- 无限扩展模型、向量库或前端动画；这些不会替代可靠演示和可复现评测。

## 推荐执行顺序

### 两周冲刺版

1. 阶段 0：收口、提交、README、演示。
2. 阶段 1：业务字典。
3. 阶段 2：收藏和反馈。
4. 阶段 3：至少 30 条评测样例和真实报告。
5. 阶段 6：完善 README、视频和简历表述。

### 有一个月的版本

在两周版基础上完成阶段 4、5，再根据真实的慢查询和超时数据决定是否做异步任务。

## 最终完成标准

一名面试官能在 5 分钟内看到并验证：

1. 系统能安全地把问题转为受权限约束的查询。
2. 用户能追问、刷新恢复、排序并导出脱敏结果。
3. 管理员能维护术语，用户能收藏和反馈结果。
4. 项目有可复跑评测，而非只凭主观展示质量。
5. 你能用真实测试、trace 和工程取舍回答深入问题。
